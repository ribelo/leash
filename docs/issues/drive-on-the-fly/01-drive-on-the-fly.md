# Drive on the fly: JEV operates without a playbook

## Status — 2026-10-04

Superseded by [L56: the pilot loop](<../pilot/01-pilot.md>), under [ADR-0012](<../../adr/0012-the-pilot-drives.md>). The reference-like JEV action loop and its target/freshness guards remain as the navigator for bounded legs; JEV-first mission ownership and DONE as mission completion do not. The recorded L45 acceptance is historical.

## Problem Statement

The operator wants to give Leash one mission and let JEV operate the browser itself, immediately, as jev-ultrafast does. A playbook is reusable know-how, not permission to work. Installing no playbooks, installing one, installing many, or installing only unrelated playbooks must never turn a usable browser task into a playbook-authoring task or a planner handoff.

Leash already has the same eight dynamic operator choices as jev-ultrafast. Its missing capability is not a hypothetical new navigation/extraction action set. The current fallback is still contracted as a small UI goal, returns an element snapshot without the operator's page-text result, hard-codes 30 steps, and inherits choices and completion guards from a playbook runner. L44 repaired initial navigation from about:blank and the erroneous no-playbook planner escalation; its acceptance was opening Example Domain, not autonomous multi-step forms or collection. The operator has not accepted that as the finished capability.

## Solution

`leash drive` has two execution lanes behind one request. An installed, suitable playbook uses the existing playbook/procedure/operator levels. Otherwise execution goes straight to the operator level with the entire mission, current page, and no planner, discovery turn, generated procedure, prepared script, or playbook prerequisite. Once on the fly, the same JEV operation/target loop follows links, fills forms, selects choices, scrolls, waits, and returns the observed result.

**Binding operator decision, 2026-09-30:** on-the-fly operation and collection follow the researched jev-ultrafast behaviour. Earlier Leash decisions that prevent it are superseded, including the blanket prohibition on records reaching models. This is not a proposal to choose between a model-free extractor and generated code. jev-ultrafast does neither: visible page text reaches JEV, a small LLM generates field values only, and the returned result is the final observed page and execution state, not a model-written record list. Leash will expose that same useful result without pretending it is exhaustive, schema-validated extraction.

| Installed playbooks | Route |
| --- | --- |
| None | No playbook/procedure choice and no planner call; enter the operator directly. |
| Exactly one potentially suitable book | JEV chooses that book or NONE from mission plus current page; never force a book solely because it is the only one. |
| Many books | JEV chooses one identified book or NONE; never merge procedures from unrelated books. |
| Books exist, none serves this mission | NONE enters the operator directly on the same page; it is not BLOCKED, a discovery request, or a reason to call Luna. |

"No blocking" here means no blocker caused by playbook availability or selection. jev-ultrafast itself has BLOCKED, finite budgets, stale/error stops, and a caller-supplied starting URL; those honest browser limits remain.

## Implementation Decisions

- **One orchestration seam.** Run owns mission routing and the existing playbook/procedure levels; Drive owns the on-the-fly operator loop. The no-book and NONE paths call that same operator with the entire mission and the caller's remaining budget, never a generated one-step procedure. Models supplies validated JEV and text-helper calls. Planner remains for explicit discovery and applicable playbook repair, not on-the-fly execution, route review, or unmet fallback expectations. A procedure-level NONE enters the operator without replaying already executed procedures; it retains actual progress/history and the current page.
- **Playbooks are optional routing knowledge.** Candidate identities are loaded book identities, not a hostname that may collide across several books for one site. Fit is judged from mission, current page, site/entry and description, not host equality alone. Even one book competes with NONE. With no candidates, there is no selection call. Hierarchical selection keeps every question at most 255 choices including NONE, does not merge books, and reports extra routing calls. Selecting NONE is a normal successful route transition, not an exceptional stop.
- **Start context.** Add an explicit `--url` starting URL to the single drive request, matching the reference's separate URL and goal. It is used to create/start a drive-owned tab, not overwrite an already populated supplied tab. Retain L44's one-explicit-HTTP(S)-mission-URL bootstrap on a blank tab when the separate start URL is absent. Do not invent a search engine, infer a secret login, or ask JEV to navigate from about:blank. On a blank tab with no `--url` and no single unambiguous mission URL, installed books are offered first: a chosen book's `entry` is the start page and the run continues. Missing-start context remains only when no books are installed, or JEV chooses NONE, and no start URL remains. It is not a playbook failure. No books means no selection call. A dry run still does not navigate, so it does not open an entry; a blank dry run with no start URL reports the missing start without a model call.
- **Observation, not a screenshot agent.** Use the same numbered table and reference identity as snap, with a guarded acquisition of viewport text, current form values, scroll state and semantic freshness. Default model state has no screenshot. The observable contract is one consistent page state; the current multi-CDP acquisition must reject/retry an inconsistent read rather than sending mixed states. Do not introduce a second DOM reference vocabulary. The reference performs this in one DOM evaluation; Leash must measure its actual observation/CDP cost rather than assert it already does the same physical read. Omit password/file/hidden controls, nonvisible/disabled/readonly edit targets and covered input. Native SELECT candidates identify an observed row plus observed option. Bounds match the reference: 6,000 viewport-text characters, at most 250 offered action candidates, ten recent actions, and explicit omitted/truncated fields; all choice heads remain below 256 options.
- **Exactly the reference's operator vocabulary.** CLICK includes link navigation, suggestion selection, native form submission and clicking date widgets. SELECT chooses a native observed option; TYPE_TEXT fills an observed editable row with the text helper's value. Page scroll moves 560 CSS pixels up/down; WAIT is 100 ms. There is no model NAV, BACK, NEW_TAB, PRESS or EXTRACT operation in the researched reference. Leash's separate nav/new/press/text/eval commands do not imply those operations are available to JEV. Initial navigation is deterministic bootstrap; subsequent navigation comes from CLICK. A new window/tab, nested scroll container, frame, shadow root, upload, canvas or keyboard-only widget is an explicit unsupported-state stop, not grounds for claiming parity with a capability the reference lacks.
- **Predict, validate, execute, then observe.** One System One request carries operation and speculative compatible target heads. Only the selected operation's target head can execute. The helper runs only for TYPE_TEXT, receiving original goal, selected field/current value, title, viewport text and six recent actions; accept only the exact text-object contract and a nonempty string no longer than 2,000 characters. Missing/invalid text ends without typing. Revalidate before helper work and immediately before input; cache text only for an unchanged context. Resolve current geometry and hit-test; model output supplies neither coordinates nor selectors. Record successful input before the post-action observation. Settle autocomplete up to 200 ms; other input up to two animation frames or 50 ms.
- **Reference budgets and stop order.** Default 60 browser actions and twice that many predictions; the action count excludes DONE/BLOCKED and refused stale input, while predictions include discarded decisions. At the action cap, a terminal DONE/BLOCKED decision is still allowed, but another browser action is not. Retry a stale observation at most ten times, with 20 ms between attempts; stale decisions re-enter the loop within the 120-prediction budget. Never retry an input whose mutation outcome is uncertain. The existing public mission deadline remains 900 seconds, caller-adjustable with --deadline-s, and still bounds routing, provider retries and settling. The operator receives the remaining mission budget; its internal 120-second default is not an extra hidden fallback cap; the reference has no comparable whole-mission deadline, so this is an explicit Leash resource boundary. Three successive unchanged non-WAIT actions produce stall BLOCKED; WAIT is excluded from that heuristic but never from budgets. Fingerprints include text, actions/form state, URL and scroll, not incidental animation geometry. Do not add confidence-triggered planner detours or stop merely because no playbook exists.
- **Unseen-page BLOCKED rescue — deliberate deviation from jev-ultrafast (fly-vnf1, fly-8fgl).** At commit 1231850a, agent.py treats a chosen BLOCKED as terminal immediately: status becomes blocked and the loop returns (https://github.com/browser-use/jev-ultrafast/blob/1231850a0bf1a0c0341fe408ef1668dbbfdfac46/jev_ultrafast/agent.py#L93-L100). Leash does not, in one bounded case. Evidence, 2026-09-30: on Google Flights from the EU, a fresh profile is redirected to consent.google.com. The reference's own snapshot.js plus model.choose picked BLOCKED 3/3 (probability 0.66-0.72) with SCROLL_DOWN offered; the consent buttons were below the fold, so the viewport the model saw did not contain them. Accepting that BLOCKED ends the mission before the page has been seen. Rule: BLOCKED is not terminal while the current page can still scroll and a scroll frontier has not yet been observed for that URL in this drive. Leash then performs the progress operation the model offered — SCROLL_DOWN first, then SCROLL_UP if the top is still unseen — and asks again. The bound is the page end (both frontiers observed) or 3 rescues per URL, and never past the action cap. Each rescue is an executed input recorded in operator_state history with model_operation still blocked, rescue true, and the step's original operation distribution (the model's BLOCKED probability, not a rewritten 1.0 on the scroll). A dry run records the prediction and dispatches nothing. Once both frontiers have been seen, the rescue budget is spent, the model did not offer the needed scroll, or the action cap is already met, BLOCKED stands. This does not remove the stall rule, the prediction cap, or a BLOCKED on a fully observed page. It is not a new model operation. A click that destroys the execution context is a document load, not one of those 20 ms stale retries: the operator waits it out with the existing 30-second load bound, then observes the new page (fly-qr70). The first live Flights attempt aborted in that 200 ms window after Accept; the failure is kept.
- **Completion is observable, not omniscient.** The prompt requires all requirements visible, selected autocomplete results, submitted searches, explicit requested filters and already-satisfied controls left alone, exactly as the reference. Without caller expectations, DONE is explicitly JEV's opinion. With expectations, fresh deterministic checks must pass or return unmet-expectation evidence; they never create a planner/handoff in the operator lane. Preserve distinct done, blocked, limit, deadline and error outcomes, and record the cause (JEV choice, semantic stall, observation retry exhaustion, prediction/action cap, missing field, unsupported state, dialog or provider failure). Dry run observes and predicts once with no bootstrap, text helper, input or output-file mutation.
- **Collection follows the actual reference, not an imagined extractor.** The on-the-fly reply adds a bounded `operator_state` containing status/reason, final page (URL, title, viewport text, indexed elements and values, scroll/omission/truncation fields), action history, prediction trace and usage/timings. All termination paths retain the last valid partial state, including before a temporary tab closes. JEV sees the same page text, including visible titles/prices/records; the text helper may see those records when generating a field value. No EXTRACT head, row-region extraction planner, one-off script generator, LLM-written answer, deduplication or all-pages collector is invented. This is a useful bounded information result, not a normalized record schema or proof of exhaustive collection.
- **Keep output modes explicit.** Prepared collectors retain their validation, bounded data summary, dedupe/repeat completion and model-free script payloads. On the fly, do not synthesize `data.records` counts from arbitrary page prose. For `--out`, use discriminated JSONL entries: `script-record` carries a prepared script record and provenance; `operator-state` carries one terminal reference-like operator state. Declare the output kinds in the reply, including a mixed run that collects by script before entering the operator; never silently append incompatible untagged shapes. Normal replies still contain operator_state without requiring --out. This is pre-1.0 protocol/output-shape work, not a compatibility shim.
- **Safety matches indexed operation, not read-only browsing.** jev-ultrafast has no general non-mutating default: CLICK can submit a form, and its flight goal explicitly stops before booking. Normal drive likewise has no new global read-only/confirmation gate. The user's mission supplies the task authority, not instructions embedded in page text. Retain ownership, private pipe CDP, capability boundaries, static service-owned observation/action code, dialog stops and explicit handoff. Preserve discovery's separate dangerous-action policy; it does not govern the operator lane. Ordinary logs contain timings/counts/usage, not viewport records, typed values, cookies or API keys. Do not log entire model requests to prove the model-data change.
- **Measure the costs that matter.** Zero books means zero upper-level/planner calls; NONE never triggers a planner review. Each normal action cycle has one JEV prediction, plus a helper only on TYPE_TEXT; stale decisions and existing transport retries are separately visible. Report provider cost when supplied, otherwise unknown, not zero or invented prices. Record bootstrap, observation, prediction, helper, action, settle and end-to-end time separately. The acceptance target is correct autonomous outcomes and this call discipline, not an unsupported promise of 7.1 seconds through a different endpoint.

### CLI delta (one protocol request)

```text
leash drive MISSION [--tab TAB] [--url URL] [--max-steps N]
                    [--deadline-s S] [--max-procedures N]
                    [--expect SENTENCE]... [--out FILE] [--dry-run]
```

--url is an optional explicit HTTP(S) start, not a model-produced navigation target. --max-steps is a positive on-the-fly executed-action cap (default 60); its prediction cap is twice that value, including stale decisions. --deadline-s retains the existing positive whole-mission budget (default 900 seconds); --max-procedures remains the playbook-lane cap (default 40), not the operator action cap. --tab, repeatable --expect, --out, --dry-run, owner/config precedence and machine-readable reply/error conventions stay consistent with the existing CLI/protocol. Start validation fails promptly and noninteractively with a correct --url example; missing start context never waits for a human prompt. The bundled skill and drive --help must describe both routes and show these examples, including an information result whose output kind is operator-state:

```sh
leash drive 'Open Travel and return the visible titles and prices' \
  --url https://books.toscrape.com/ --out travel-state.jsonl
leash drive 'Complete this page search and open the matching result' \
  --tab TAB --max-steps 60 --deadline-s 300
```

A caller reads the terminal status and verification fields rather than interpreting a successful control request as proved mission success. Repeating a form-submit mission is not generically idempotent: retain actual executed-input evidence after interruption and do not automatically rerun uncertain mutations. There is no new confirmation flag, interactive questionnaire, browser server or second CLI request hidden inside this command.

### Blank-tab playbook entry, 2026-09-30 — fly-b6yt fly-xger

**Finding.** On the installed service (master 094deda), with the books.toscrape.com playbook installed and a blank tab, `leash drive "collect every book title and price in the Mystery category" --out /tmp/mystery.jsonl` returned `blocked`, 0 model calls, `playbook_choices` empty, reason `no starting page: provide --url with one HTTP(S) URL without userinfo, one unambiguous URL in the mission, or --tab on an open page`.

**Cause.** `initial` required a start URL whenever the tab was `about:blank`, before playbook choice. An installed book's `entry` never got to supply the start page. That regressed L40, where a blank-tab mission chooses the playbook and the playbook navigates to its entry, and it broke the operator rule that drive works with one playbook, with many, and with none.

**Fix.** On a blank tab with no `--url` and no single unambiguous HTTP(S) URL in the mission, playbook choice runs first when any books are installed. A chosen book navigates to its `entry` and the run continues. The same missing-start reason remains only when no books are installed, or JEV chooses NONE, and no start URL remains. No books still means no selection call. A supplied start URL, including one unambiguous URL in the mission, keeps the previous bootstrap: navigate there, then route. A dry run still does not navigate. JEV is still never asked to navigate from `about:blank`.

### Researched reference — what jev-ultrafast actually does

Research cloned the public repository with the requested shallow clone. These are source observations at commit `1231850a0bf1a0c0341fe408ef1668dbbfdfac46`; no benchmark was rerun here.

- [README: dynamic indexed policy](<https://github.com/browser-use/jev-ultrafast/blob/1231850a0bf1a0c0341fe408ef1668dbbfdfac46/README.md#L19-L51>) lists precisely CLICK, TYPE_TEXT, SELECT, SCROLL_UP, SCROLL_DOWN, WAIT, DONE and BLOCKED. One prediction answers operation and speculative compatible target heads together. No prepared per-site script/field strings.
- [Prompts and 60-action budget](<https://github.com/browser-use/jev-ultrafast/blob/1231850a0bf1a0c0341fe408ef1668dbbfdfac46/jev_ultrafast/questions.py#L3-L26>) require the whole goal, visible completion evidence, autocomplete selection and search submission; page text is untrusted. [Model request construction](<https://github.com/browser-use/jev-ultrafast/blob/1231850a0bf1a0c0341fe408ef1668dbbfdfac46/jev_ultrafast/model.py#L60-L146>) sends URL/title/text, indexed elements/current values and ten recent actions to JEV. [The only generative helper](<https://github.com/browser-use/jev-ultrafast/blob/1231850a0bf1a0c0341fe408ef1668dbbfdfac46/jev_ultrafast/model.py#L150-L198>) produces a field-value JSON object, not collected data or code.
- [Atomic DOM snapshot](<https://github.com/browser-use/jev-ultrafast/blob/1231850a0bf1a0c0341fe408ef1668dbbfdfac46/jev_ultrafast/snapshot.js#L44-L107>) yields viewport controls, values/state, visible text bounded at 6,000 characters, at most 250 action candidates, node references, semantic guards, omitted count and 560-pixel page scrolling. Password/file/hidden and disabled controls are excluded. Screenshots are optional inspector/recording data, not default JEV input.
- [Browser start and observation](<https://github.com/browser-use/jev-ultrafast/blob/1231850a0bf1a0c0341fe408ef1668dbbfdfac46/jev_ultrafast/browser.py#L26-L83>) create/attach one target, deterministically navigate to the caller's URL, wait for the initial document, then observe. [Input/settle](<https://github.com/browser-use/jev-ultrafast/blob/1231850a0bf1a0c0341fe408ef1668dbbfdfac46/jev_ultrafast/browser.py#L100-L194>) validates guards, resolves/hit-tests targets, clicks links/forms, fills text with keyboard input, sets native selects with input/change events, scrolls or waits. There are no policy-level arbitrary nav/back/new-tab/press actions and no general read-only policy.
- [Agent state, retries and loop](<https://github.com/browser-use/jev-ultrafast/blob/1231850a0bf1a0c0341fe408ef1668dbbfdfac46/jev_ultrafast/agent.py#L38-L165>) return the final page plus history, decisions/predictions and helper usage/timing; allow 60 executed actions/120 predictions; refresh on stale decisions within the prediction budget and retry a stale observation up to ten times at 20 ms intervals; record execution before observing; stop on JEV DONE/BLOCKED or three unchanged non-WAIT actions. Non-stale errors propagate rather than silently retrying an uncertain mutation; the Flights example preserves partial state in its finally block. Leash must expose those errors through its existing typed terminal reply. DONE is a policy decision, not a verification guarantee.
- **No extraction feature is hidden here.** There is no EXTRACT operation, collection-schema output, generated one-off script, row-region extractor or model answer synthesis. Final page text is data returned to the caller and also sent to JEV. [Flights verification](<https://github.com/browser-use/jev-ultrafast/blob/1231850a0bf1a0c0341fe408ef1668dbbfdfac46/examples/flights.py#L18-L64>) reads page text with deterministic code outside the agent, checks route/date/results, saves the state, and fails if it is wrong; it does not book a flight or produce an exhaustive fare dataset.
- [Current performance report](<https://github.com/browser-use/jev-ultrafast/blob/1231850a0bf1a0c0341fe408ef1668dbbfdfac46/docs/performance.md#L1-L55>): recorded one-goal Flights run **7.073 s**, 17 JEV requests, 10 interactions plus one WAIT, two generated field values (**581/346 ms**), median JEV latency **178 ms**. Six alternating matched runs (three pairs) compare the original frozen runtime with this optimized runtime: medians **9.450/7.092 s**, all **3/3 independently verified** in each arm, median requests **22/17** and protocol calls **1,092/101**. Both arms use the same goal, browser/profile/viewport, TypeSafe JEV and Mercury helper; a three-pair comparison is too small for a broad statistical/reliability claim (reported sign-test p=0.25). The recording's **$0.00006272** is only the two OpenRouter helper calls: TypeSafe exposes tokens, not billed dollars, so total task cost is unknown. Browser setup, initial navigation and post-run verification are outside the loop clock. Separate Wikipedia **2.798 s** and local hotel **1.896 s** checks are smoke tests, not matched speed comparisons. Changed-code diagnostic runs and a six-call helper probe are not general semantic-accuracy benchmarks.
- [Historical prepared prototype](<https://github.com/browser-use/jev-ultrafast/blob/1231850a0bf1a0c0341fe408ef1668dbbfdfac46/docs/performance-prepared.md#L3-L42>): 12.884 s, 17 JEV requests, 11 actions, **zero generated text calls**, five ordered goals and quoted city strings. The local hotel fixture's 1.086/1.242/1.311 s runs omit live-site loading. Neither is the current one-goal, generated-text result.
